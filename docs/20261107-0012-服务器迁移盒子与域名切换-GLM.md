> 背景：2026-11-06 排查发现自有服务器两个入口全部失联，本轮完成服务器考古、
> 新部署链路搭建与域名切换。

## 一、失联真相（考古结论）

| IP | 角色 | 现状 |
|---|---|---|
| 18.225.92.148 | 10-30 迁移后的"正式服务器"（文档记录） | SSH banner 超时，实例已回收 |
| 18.223.172.239 | oh.sbbz.tech 当时的 A 记录指向 | 端口 TCP 通但无服务应答——EIP 已释放重分配 |
| 18.191.80.90 | **play.sbbz.tech 的 CF 源站记录**（10-30 迁移时漏改！） | 早已死亡 → CF 522 的直接原因 |
| 34.222.204.54 | InstaBox 盒子 box-c6119b 的出网 NAT IP | **不是入站地址**（见下） |

**三个关键认知（都实测验证）**：

1. **真正一直在服役的"服务器"是 InstaBox 盒子 `box-c6119b`**（2026-10-26 创建，跑着"免流
   节点"项目的 bz/xbz 代理服务 + acme.sh 证书续期）。10-31 前后上任助手已把游戏部署上去：
   docker 容器 `sakura-web`（nginx:alpine，0.0.0.0:8090→80），站点根 `/data/home/sakura`，
   公网入口 = InstaBox 发布端口 URL。所谓"AWS 服务器"在 10-30 前后就没了。
2. **InstaBox 盒子没有公网入站**。`curl icanhazip` 返回的 34.222.204.54 只是出网 NAT 的
   egress IP，不路由入站；`nc -z` 显示"端口通"是平台边缘代答 SYN 的假象。判定方法：
   盒内起临时 HTTP 服务，外部直连 IP 立刻现形（本轮实测 HTTP 000）。
   这意味着"自有域名 + 自己的证书 + 固定端口"的旧架构在盒子上**不可能复活**。
3. 盒子的公网入口只有一种：**已发布端口**（`instabox port publish`），URL 形如
   `https://8090-<boxid>.instabox.tech`，TLS 由平台边缘终结（*.instabox.tech 证书）。

## 二、本轮搭好的部署链路（全部实测 ✓）

```
git push gitee main
   └→ 盒子 root cron（*/3）/root/sakura-deploy.sh
        git fetch（gitee 主源，失败回退 github）→ 无新提交即退出
        → git reset --hard → rsync --delete --delete-excluded 到 /data/home/sakura
        → 健康检查 http://127.0.0.1:8090/ → 失败自动回滚上一提交
   └→ 容器 sakura-web（8090 明文，instabox 发布 URL）
      容器 sakura-tls（2096 TLS，acme 通配符证书只读挂载——备用，见"遗留"）
```

- 仓库克隆在盒子 `/data/home/gayme-deploy`（origin=gitee 含令牌、github=备源；**令牌只存在
  盒子私有盘，不入仓库**）。
- rsync 用 `--delete-excluded`：站点根只保留运行文件（docs/tests/tools/经验 不落地）。
- 手动通道：`bash tools/deploy_box.sh`（instabox push → 暂存区 → 盒内 rsync → 健康检查）。
  注意 instabox push 会按本地目录名落盘（`.../gayme/`），所以必须先推暂存区再同步，
  否则会把仓库嵌套进站点根（本轮踩过并已修正）。
- 健康入口：https://8090-agqxoy6u363jxgfufg2onqxbm4.instabox.tech/ （实测 v3.4.35 ✓）
- 另一个项目占用的资源没动：127.0.0.1:8080（oneknife999 的 python 服务）、宿主 8443、
  bz/xbz 服务、in*.sbbz.tech 记录。

## 三、域名切换（DNS 已改，差一条面板规则）

旧 A 记录全部指向死亡 IP（oh 的 IPv4+IPv6、play 的 18.191.80.90），已通过 CF API
（cfut_ 令牌，DNS 编辑权限实测可用）替换为：

```
oh.sbbz.tech   CNAME → xbzsb-sakura-letters.static.hf.space   （proxied 橙云）
play.sbbz.tech CNAME → xbzsb-sakura-letters.static.hf.space   （proxied 橙云）
```

**还差最后一步（API 令牌没有 Rulesets 权限，必须面板操作，约 2 分钟）**：
Cloudflare 面板 → sbbz.tech → Rules → Origin Rules → 创建规则：
- 匹配条件：Hostname in { `oh.sbbz.tech`, `play.sbbz.tech` }
- 操作：**Host Header → Rewrite to** `xbzsb-sakura-letters.static.hf.space`

原理：CF 源站连接的 SNI 随改写后的 Host 走，HF 边缘凭 `*.static.hf.space` 证书应答并按
Host 路由到 Space。规则生效后 `https://play.sbbz.tech/`（不带端口！）即恢复，
`oh.sbbz.tech` 同理。当前未加规则时两域名报 525（CF↔HF 握手失败）——这是预期过渡态。

## 五、遗留与建议

1. **等你 2 分钟**：面板加 Origin Rule（第三节），两个自有域名即复活。
2. sakura-tls 容器（2096）保留作备用：一旦盒子未来获得真实入站、或迁移到任何有入站的
   主机，把 `/data/home/sakura`+`sakura-tls/conf.d`+acme 证书原样挂载即插即用。
3. 盒子与"免流节点"项目混部——资源冲突已规避（端口/域名/记录都分开），但盒子被两个项目
   依赖后，删盒子前要先迁走两边。
4. 旧文档勘误：20261030 迁移文档里"新实例 18.225.92.148"的判断有误（那只是当时的边缘
   IP 漂移）；play.sbbz.tech 源站漏改是 522 挂了整整一周的直接原因。
