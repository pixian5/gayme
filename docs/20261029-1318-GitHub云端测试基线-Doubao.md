## 四、云端环境要求（结论）

- Node ≥ 22（本机基线 v24.21.0，npm 12.1.0）；纯前端零构建，**不需要 Python / 虚拟环境**
- `npm ci` 不会下载浏览器内核；浏览器回归前需 `npx playwright install chromium`（约 150MB，一次性）
- pre-push 钩子（`.githooks/pre-push`）只跑静态测试 + 语法 + diff，**不依赖浏览器**，
  云端可以正常 push；需要 e2e 时设 `PREPUSH_E2E=1`
- 只跑静态门槛（`npm test` + `test:syntax`）时无需安装 chromium，最低资源路径

## 五、三远程分工（写入 README「远程仓库与云端测试」）

- `origin` = gitee：**服务器部署主源**（root cron 每 3 分钟拉取 → oh.sbbz.tech:8080）
- `github` = 公开 GitHub：**云端克隆 / 云端测试主源**，Trae 云端沙箱从这里拉代码
- `gitcode` = 第三备份（另一条并行开发线）

注意：云端在 GitHub 提交后，必须再把 `main` 同步到 gitee，否则服务器不会部署到最新版本。

## 七、经验

- **推送前先 `git fetch --all`**：该项目存在多机/多模型并行提交，GitHub 曾落后 2 个提交而不自知
- 远程命名不等于角色：`origin` 是 gitee 但「云端源」是 `github`，分工必须写进 README，避免误判
- 用 `git merge --ff-only` 校验线性关系：失败即说明有分叉，应先看 `git log HEAD..origin/main`
- 验证云端可用性的最低成本方式：`git clone --depth 1` 到 `/tmp` 后 `npm ci` + 逐个跑测试，
  能同时暴露「资源未入库」「脚本依赖本地环境」「忽略规则误伤」三类问题
- 公开仓库可用 `raw.githubusercontent.com` / API `contents` 直接核对资源清单，不必登录
