## 二、P0：Service Worker（花了最多功夫，结论与初审不同）

### 2.1 初审判断（部分正确）

`sw.js` 原代码：

```js
const fetching = fetch(req).then(...).catch(() => hit);
return hit || fetching;
```

当缓存未命中（`hit` 为 `undefined`）且网络失败时，`.catch(() => hit)` 返回 `undefined`，
`respondWith` 解析成 `undefined` → Firefox 报错。**这是真 bug，已修**：全部失败分支改为返回
`offlineResponse()`（504），且整个处理链用 `async` 包起来、全路径 `try/catch`。

### 2.2 但修完仍失败——四组实验定位真因

修完 `undefined` 后连跑 6 次，**仍 2/6 失败**。于是做二分实验（每组 6 次官方 `npm run test:e2e:firefox`）：

| 实验 | 媒体请求处理方式 | 结果 |
|---|---|---|
| A | **完全不拦截**（`if (isMedia) return;`） | **6/6 通过，0 错误** |
| B | 拦截，去掉后台刷新请求 | 0/6，每轮报错 3~7 条 |
| C | 拦截 + 媒体层安装期预缓存立绘 | 0/6 |
| D | 拦截 + 立绘画进核心层 `PRECACHE` | 0/6 |

C / D 里立绘确实进了缓存（用探针读过 `caches.keys()`，5 张都在），**依然失败**。
结论：报错由「**SW 拦截媒体请求**」这个行为本身触发，与响应是否正确无关——
页面刷新时 in-flight 的媒体请求被取消，Firefox 就报 `unexpected error`，
即使我们已经保证 `respondWith` 永远 resolve 出合法 Response。

### 2.3 最终取舍

媒体资源（`/audio/`、`/assets/cg/`、`/assets/portraits/`）**不再由 SW 拦截**，交给浏览器原生加载：

- **收益**：Firefox e2e 连跑 6 次 **6/6 通过、0 控制台错误**；玩家刷新页面时立绘不再加载失败。
- **代价**：离线时 BGM / CG 不可用，立绘回退内联 SVG（引擎 `PORTRAIT_BITMAPS` 已内置该降级，
  见 `js/engine.js:410`）。核心层（HTML / CSS / JS / 字体 / 图标）仍预缓存，**离线可玩不受影响**。
- 立绘不再进 `PRECACHE`——不拦截就用不上，避免每次发版白白多下 476KB。

`respondWith` 的全路径兜底作为健壮性改进保留（防止以后任何分支再出现 `undefined` / reject）。

### 2.4 一句话经验

> **e2e 偶发失败，先做「改一处 → 跑 6 次」的对照实验，别急着下结论。**
> 这一步我一开始判成「respondWith 解析成 undefined」，修完只剩 4/6；
> 真正根因是「拦截行为本身」，靠四组实验才逼出来。

## 三、P1：移动端三处溢出

三处都缺移动端适配（`@media (max-width: 768px)` 里没有对应规则）。

| 玩法 | 原因 | 修法 |
|---|---|---|
| `d5_piano` | `.pi-key` 固定 `width: 48px` × 8 键 + gap + padding，在 390px 视口整体超宽约 24px | 移动端 `.pi-key { flex: 1 1 0; min-width: 0; width: auto }`，键宽按可用宽度均分；`.pi-piano` 加 `max-width: 100%` |
| `d4_reflection` | `maxOffset` 写死 120px，初始偏移 84px 把倒影文字推出舞台，被 `overflow: hidden` 裁掉 | `maxOffset = clamp(stageW × 0.18, 36, 120)`，390px 视口下约 63px；舞台高度与字号同步收敛 |
| `d5_sugar` | 格子固定 56px，糖块用「百分比 left + 固定 px 宽」定位，多格宽的块会被挤出舞台右边 | 格子按舞台宽度收敛；新增 `clampRatio()`，所有写 left / top 的地方（初始、拖动、吸附落位）都先夹回可视范围 |

修复后截图（`gayme-audit-v3.4.32/screenshots/fix-*.png`）显示三处均完整落在视口内，
`document.scrollWidth === 390`。

## 四、新增回归：移动端玩法溢出扫描

人工扫 95 个玩法节点只能扫一次，留不下防线。新增 `tests/browser/overflow.e2e.mjs`
（`npm run test:overflow`）：390×844 视口逐一挂载全部玩法节点，检查是否有元素横向溢出视口。

两个坑（已写进脚本注释）：

1. **玩法节点没有统一字段**。节点用的是各自 kind 字段名（`piano` / `reflection` / `sugar` …），
   `minigame` 只是另一类老玩法（6 个）。脚本从 `js/games/*.js` 的 `register("xxx")` 提取 kind 清单再筛选。
2. **玩法浮层挂载有延迟**。打字机结束后才挂载，后日谈三处实测要 ~1.4s，等待不足会误报。

实测：**95 个玩法节点，横向溢出 0 个**。
