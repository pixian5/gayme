# v3.4.60：部署后自动自检与告警

日期：2026-11-28 20:38 · 模型：Doubao

## 为什么做

v3.4.59 有了 `verify_release.sh`，但仍然要人记得在发版后跑一次。3.4.57 的账号版本滞后、
3.4.57 的账号版本滞后与响应头异常都属于「部署脚本自己觉得成功、线上其实不对」——把自检挂到部署流程末尾，
才能在没人盯着的时候发现。

## 做法

`tools/box_cron_deploy.sh` 在 `health_check` 通过、写入「部署成功」之后，调用一次公网自检：

```bash
GAYME_SITE_URL="$PUBLIC_URL" GAYME_EXPECTED_VERSION="$VER" bash "$REPO/tools/verify_release.sh"
```

- **只在新提交部署时跑**：脚本在 `PREV = CUR` 时提前退出，自愈与补文件不触发，不会每 3 分钟推一次告警。
- **失败不回滚**：自检项里 nginx 响应头、DNS、缓存、目录排除都不在仓库里，回滚代码解决不了；
  回滚还会把已经可用的站点拉回旧版。因此失败只写日志 + Bark 告警，部署结果仍算成功。
- **告警内容**：取前 3 条「失败」原因拼成一行，标题「樱时信笺·发版自检」，与备份脚本共用
  `/root/.sakura-bark`；没有该文件就只写日志。
- **可关闭/可改地址**：`SAKURA_SKIP_PUBLIC_VERIFY=1` 跳过；`SAKURA_PUBLIC_URL` 改自检地址；
  `SAKURA_BARK_FILE` 换告警文件（离线测试用）。
- 日志新增两行：`发版自检通过：通过 N 项，失败 0 项` 或 `!! 发版自检未通过（…）`。

## 离线测试补强

`tools/test_box_cron_deploy.sh` 新增：

- 假的自检脚本（真脚本另由 `tools/test_verify_release.sh` 覆盖）：记录调用参数，可用 `verify_fail` 标记失败。
- 假 curl 增加 Bark 分支：`-X POST` 记为 `bark …`，不真推送。
- 断言：无新提交不调用自检；部署后调用一次且带 `SAKURA_PUBLIC_URL`；通过时日志写明项数且不发告警；
  自检失败时退出码仍为 0、站点版本不回滚、不写 `failed.sha`、Bark 收到告警。

## 踩坑

- **BSD 的 `tr` 不能拿多字节字符当替换目标**：原先用 `tr '\n' '；'` 拼多条失败原因，
  macOS 上写进日志的是截断后的乱码（`失败: 假自检失败�`）。改用 `awk` 显式输出分隔符。
- 测试里 `verify_release.sh` 若继承 stdout 管道，结束后管道不关会导致「测试卡死」——
  与 v3.4.59 测试同因，后台进程输出一律重定向到文件。

## 现场情况

盒子上 `/root/.sakura-bark` 此前**缺失**，告警会静默丢弃。本轮已按备份脚本同一格式补建
（内容为一条推送地址，权限 600）；之后部署自检失败与备份失败共用这条通道。

## 验证

- `bash tools/test_box_cron_deploy.sh` 全部通过（含新增两条）。
- 盒子实测：空提交 `4b366c9→41993f6` 部署后，日志按顺序出现「部署成功 … v3.4.60」与
  「发版自检通过：通过 20 项，失败 0 项」；`/root/sakura-deploy.sh` 与仓库版本 md5 一致。
- `bash tools/test_verify_release.sh` 6 情形全过；`npm test` 71/71；语法、账号 36/36、nginx 9 情形全过。
- 本版部署后：盒子日志出现「部署成功 … v3.4.60」；下一次新提交部署时应出现「发版自检通过」。

## 回滚

把 `box_cron_deploy.sh` 里 `public_verify || true` 一行删掉即可；已安装到盒子的脚本会在下次部署时自更新回旧版。
告警文件与日志不影响游戏。
