# 樱时信笺（Sakura Letters）剧情梳理与开发建议

> 版本：v2.7.7（Demo）  
> 梳理时间：2026-08-10  
> 基于 `js/script.js`、`js/engine.js`、`js/minigames.js`、`js/saves.js` 及 `docs/` 历史文档整理。

---

## 一、项目概述

| 项目 | 内容 |
|------|------|
| 中文名 | 樱时信笺 |
| 英文名 | Sakura · Letters · in · Cherry · Time |
| 类型 | HTML5 视觉小说 / 校园群像 / 时间循环叙事 |
| 当前版本 | v2.7.7 |
| 核心载体 | 浏览器端单页应用（`index.html` + CSS + 原生 JS） |
| 目标体验 | 在樱花盛开的学园里，通过“回信”帮助三位女主角走出各自的困境，并最终打破循环、写下自己。 |

**一句话定位**：一款以“写信/回信”为核心交互、以“时间循环”为骨架、以“三位女主角的个人成长”为血肉的多结局视觉小说。

---

## 二、世界观与核心设定

### 2.1 舞台
- **樱海学园**：临海高中，四月樱花大道贯穿校园。
- **时间背景**：以四月樱花季为起点，覆盖运动会、樱花祭、全国赛、省展、毕业前开放日等关键节点。

### 2.2 核心隐喻
- **樱花**：美丽、短暂、循环往复的春天象征。
- **信/回信**：不只是道具，而是“看见对方”与“写下自己”的行为。
- **循环**：时间不是惩罚，而是“用来写的”。只有替别人回信、也替自己回信，才能合成“樱花信”打破循环。

### 2.3 关键道具
- **匿名信**：由“学姐”留下，引导男主进入三条未走完的路。
- **关键词**：通过剧情节点解锁，可两两合成新关键词。
- **樱花信**：由“祭信”（樱花祭+回信）与“未寄信”（匿名信+学姐）合成，是打破循环的钥匙。

## 三、角色梳理

### 3.1 男主角：沈屿
- 高二转学生，父母冷战三个月，主动选择住校。
- 性格偏沉默、观察型，是玩家视角的容器。
- 通过回信/选择影响三位女主，同时也在循环中逐渐写下自己。

### 3.2 女主角

| 角色 | 关键词 | 核心困境 | 代表意象 |
|------|--------|----------|----------|
| **林诗雨** | 小说、角色A、外婆、法律系 | 优等生外壳下偷偷写小说，害怕被母亲发现，小说女主角永远停在“消失”那一刻。 | 蓝、稿纸、门 |
| **夏织** | 全国赛、特招、旧伤、再婚家庭 | 田径社王牌，教练被辞退，家庭破碎，只能用“跑出去”逃避，害怕停下来。 | 橙、跑道、终点线 |
| **苏念** | 紫、挣、哥哥、省展金奖 | 天才画家，三年前哥哥去世后一直画“紫色”而无法完成新作，被自己按在草稿里。 | 紫、画布、翅膀 |

### 3.3 关键配角
- **学姐**：三年前同样经历循环的转学生，三条路都走了一半，休学离开。她留下匿名信，是循环的“上一任记录者”。
- **班主任**：功能性角色。
- **父母**：通过电话/短信存在于男主背景中，冷战线是男主自己的“未寄信”。

## 四、剧情结构梳理

### 4.1 整体框架

```
序章（第1日）
    ↓
共通线（第2-4日）—— 多选项、小游戏、关键词解锁、好感度积累
    ↓
第5日路线选择 —— 玩家主动选择见谁，决定进入哪条个人线
    ↓
个人线（4章 × 3结局）× 3女主
    ├─ 林诗雨线：GOOD「回头」/ NORMAL「半章」/ BAD「未活过」
    ├─ 夏织线：  GOOD「终点线」/ NORMAL「第三名」/ BAD「一个人」
    └─ 苏念线：  GOOD「挣」/ NORMAL「网展」/ BAD「按住」
    ↓
真结局入口 —— 需三女主 GOOD 结局全通
    ├─ 普通真结局：「未破环」（未合成樱花信）
    └─ 真结局：「樱花信·破环」（合成樱花信后触发）
        ↓
后日谈「樱海以后」—— 真结局解锁
    ├─ 明信片印记
    ├─ 现实回信
    ├─ 时间线排序
    ├─ 半年后回信角（自由回信、规则、分拣）
    ├─ 毕业前留言墙
    └─ 校刊校对
```

### 4.2 序章（第1日）
1. 沈屿转学，在校门口迷路。
2. 走廊遇见班长林诗雨，发现她地图边角写着「角色A推开门——」。
3. 中午操场遇见夏织，被拉去田径社。
4. 傍晚误入美术室，遇见苏念和她未完成的紫。
5. 回家发现书包里有匿名信：「樱海有三条未走完的路，你会走哪一条？」

**功能**：介绍三位女主、埋下循环伏笔、解锁关键词（林诗雨、角色A、紫、匿名信）。

### 4.3 共通线（第2-4日）

**第2日**
- 上午四选一：图书馆（林诗雨）、操场（夏织）、美术室（苏念）、天台透气。
- 二周目/多周目追加：旧校舍后面见学姐、樱花树下回忆、找学姐问循环。
- 中午三人 cafeteria 同框。
- 夜晚进入「梦境编织」小游戏，随后第3日开场有多种小型玩法（塔罗、光谱、听诊、拼图、香水等）。

**第3日**
- 运动会预选。
- 上午根据好感度/选择进入不同女主相关剧情。
- 傍晚开始出现“第二封信”与更多心理/感官玩法（气味、温度、触觉、沉默选择等）。

**第4日**
- 拼贴诗、摄影构图、呼吸节奏等玩法。
- 晚上第三封信到：「如果三条路通向同一个地方，你还要走吗？」
- 深夜触发气味闪回、温度选择、时光胶囊交付等。

### 4.4 第5日：路线决定日
- 玩家明确选择：图书馆找林诗雨 / 操场找夏织 / 美术室找苏念。
- **不再是按好感度静默分配**，避免玩家产生被系统“抢走”的感觉。

### 4.5 三条个人线

#### 林诗雨线
- 母亲翻书包，诗雨恐惧被发现。
- 小说女主永远停在“消失”，玩家替她写一句后续。
- **GOOD**：让角色A“回头之后开始活下去”，小说投校刊，母亲最终支持。
- **NORMAL**：先写完半章，其余留给外婆和自己，考法律系但承诺继续写。
- **BAD**：建议她“真的消失一次”，诗雨转学远去，稿子停在未活过的人生。

#### 夏织线
- 教练辞退她，家庭只剩每月转账和一句“挺好的”。
- 玩家陪她计时训练，处理旧伤。
- **GOOD**：陪跑到终点，全国赛第二名，有人等在终点。
- **NORMAL**：先治脚，全国赛第三名，留校复读一年。
- **BAD**：告诉她“你自己就够了”，她独自加练受伤，休学离开。

#### 苏念线
- 省展邀新稿，她撕了47张草稿。
- 紫色是哥哥的颜色，她画紫是为了留住他。
- 玩家帮她调一次色，让她看见“自己想从紫里挣出来”。
- **GOOD**：松手让画中人出来，省展新作《挣》放在入口第一幅。
- **NORMAL**：退回邀请函，网上开小展，发现“不是我一个人”。
- **BAD**：觉得“她本来就不该出来”，休学，画布反扣。

### 4.6 真结局
- **解锁条件**：三女主 GOOD 结局全通。
- 学姐署名信出现，揭示她三年前也经历循环，三条路都走了一半。
- 樱花祭之夜，玩家替她回信，也写给自己想成为什么样的人。
- 若未合成「樱花信」：进入「未破环」LOOP ENDING。
- 若已合成「樱花信」：进入自由写信，打破循环，TRUE ENDING「樱花信·破环」。

### 4.7 后日谈「樱海以后」
真结局后解锁，时间线持续延伸：

1. **第三天**：学园收摊，三人约好每周见一次。
2. **明信片**：学姐从新城市寄来明信片，没有回寄地址。玩家选两枚印记（写下/起跑/开门/等候），补一句落款（下次见/照顾好自己/空白）。
3. **一周后**：明信片折返，学姐写“我在新城市打开了一扇窗”。玩家自由回一句给现在的学姐。
4. **时间线排序**：把“樱花祭寄信、学园收摊、收到回信、写下现在的话”四件事排序，确认日子在往前走。
5. **半年后·回信角**：旧公告栏改成署名/日期的公开信栏。玩家为第一位来信者写回信，选择回信角第一条规则。
6. **回信分拣**：三张纸条分别需要空间、一步、倾听，玩家匹配回应。
7. **又过半年·留言墙**：毕业前开放日，四张留言需要区分“公开/交还本人/暂不张贴”，核心是不能替别人决定。
8. **校刊校对**：六句话区分“已有依据/只能推测/交还本人”，避免把猜测写成事实。
9. **结局**：故事不被封存，交还给每一个正在生活的人。

## 五、游戏系统盘点

### 5.1 引擎层（engine.js）
- 单文件 IIFE 引擎，约 670KB。
- 基于节点的剧本推进：`gotoNode(nodeId)`。
- 支持分支字段：`next`、`choice`、`if/else`。
- 支持循环文本：`loopText` 根据 `loopCount` 切换。
- UI：背景、立绘（SVG）、打字机对白、日程条、好感度心条、顶部菜单、浮层系统。
- 状态管理：好感度、 personality、访问计数、循环计数、周目数、历史记录。

### 5.2 剧本层（script.js）
- 单文件数据，约 670KB。
- 定义：角色 `CHARACTERS`、立绘 `PORTRAITS`、场景标签 `SCENE_LABELS`、关键词 `KEYWORDS`、合成配方 `COMPOSE_RECIPES`、CG `CGS`、结局 `ENDINGS`、朋友圈 `MOMENTS`、剧本节点 `SCRIPT`。
- 节点字段非常丰富：`day/time/bg/char/speaker/text/next/add/set/keyword/cg_unlock/memory/inbox/moment/personality/echoSave/perspective/clues` 等。

### 5.3 小游戏/互动层（minigames.js + engine.js）
目前约 50+ 种互动类型，大致可归为：

| 类别 | 代表玩法 |
|------|----------|
| 书写/绘画 | 涂鸦、拼贴诗、自由写信 |
| 节奏/操作 | 跑步节奏、呼吸、心跳、声音模仿 |
| 选择/分类 | 塔罗、光谱、温度、沉默选择、分拣、留言墙、校对 |
| 解谜/创造 | 星座连线、信物拼图、气味调香、时光胶囊、折纸 |
| 时间/记忆 | 梦境编织、时间线排序、气味闪回 |

### 5.4 存档系统（saves.js）
- localStorage 存储。
- 支持存档槽位、结局图鉴、CG 图鉴、关键词、记忆、朋友圈、回声、设置。
- Schema v3，导出/导入 JSON，失败回滚。

### 5.5 测试（tests/）
- Node 原生测试：`npm test`
- 覆盖：剧情引用完整性、主线可达性、时间回溯标记、真结局状态、关键词解锁、互动层分发器、语法检查、静态资源等。

## 六、当前优势与亮点

1. **主题高度统一**：所有系统（写信、回信、关键词合成、循环）都服务于“看见他人”与“写下自己”。
2. **叙事与玩法融合**：小游戏不是填充，而是角色心理的隐喻（调色=让苏念看见自己、跑步节奏=跟上夏织、拼贴诗=帮诗雨重组语言）。
3. **循环结构有收束**：三周目/多周目不重复，学姐提供新信息，樱花信合成给玩家明确目标。
4. **后日谈处理克制**：不强行团圆、不召回学姐、不制造新谜题，把成长落到“每周见一次”“先问本人”等具体行动。
5. **测试覆盖较全**：节点引用、可达性、时间线一致性、互动分发器都有自动化检查。

## 七、技术债务与重构建议

### 7.1 代码拆分（最优先）
**现状**：`script.js` 和 `engine.js` 都接近 700KB，所有内容混在一个文件。

**建议**：
- 将 `script.js` 拆分为：
  - `data/characters.js`
  - `data/scenes.js`
  - `data/keywords.js`
  - `data/cgs.js`
  - `data/endings.js`
  - `data/moments.js`
  - `story/prologue.js`
  - `story/common.js`
  - `story/shiyu.js`
  - `story/xiazhi.js`
  - `story/sunian.js`
  - `story/true_end.js`
  - `story/afterword.js`
  - 最后由 `story/index.js` 统一拼装成 `SCRIPT`。
- 将 `engine.js` 拆分为：
  - `engine/core.js`：状态、节点推进、变量管理
  - `engine/render.js`：背景、立绘、UI 渲染
  - `engine/audio.js`：BGM/音效
  - `engine/save_load.js`：存档读档
  - `engine/menus.js`：菜单、流程图、图鉴
  - `engine/interactions/`：每个小游戏一个模块

**收益**：
- 多人协作不冲突。
- 单文件加载更快（可配合 ES Module 动态导入，按需加载个人线）。
- 后续做编辑器/可视化流程图更容易。

### 7.2 剧本数据与渲染逻辑解耦
**现状**：节点里同时包含叙事文本和 UI 配置（`clues`、`doodle`、`minigame` 等），引擎用大量 `if (node.xxx)` 分发。

**建议**：
- 引入“节点类型注册表”：
  ```js
  const NODE_HANDLERS = {
    choice: renderChoice,
    doodle: renderDoodle,
    minigame: renderMinigame,
    // ...
  };
  ```
- 每个 handler 独立文件，统一接口：`handler(node, nodeId) -> Promise<nextNodeId>`。
- 节点数据只描述“要什么”，具体 DOM 由 handler 负责。

### 7.3 小游戏去重与抽象
**现状**：50+ 小游戏，很多结构重复（选择-反馈-跳转、拖拽-匹配-反馈、自由输入-关键词匹配）。

**建议**：
- 抽象出通用模板：
  - `SelectionTemplate`：多选一带反馈。
  - `MatchingTemplate`：拖拽/点击匹配，支持撤回、重置、正确/错误反馈。
  - `FreeTextTemplate`：自由输入，关键词匹配 + 默认回复。
  - `SortingTemplate`：排序/时间线。
- 将具体小游戏配置化。例如“留言墙”和“校刊校对”本质都是“分类到多个 bin”，可共用 `runCategorization(config)`。
- 这能显著减少 `minigames.js` 体积，也便于新增玩法。

### 7.4 状态管理增强
**现状**：状态存在全局 `state` 对象和 `Saves` 中，部分数据（如 `visitedNodes`、`loopCount`、`playCount`）持久化，但对白历史只存在内存。

**建议**：
- 引入不可变状态快照，每次节点推进生成 `{nodeId, variables, history}`。
- 读档时直接恢复快照，而不是重新走一遍 `gotoNode`。
- 为流程图/历史回看提供完整快照链。

### 7.5 场景与资源管理
**现状**：`setScene` 通过检查样式表规则判断背景是否存在，缺失时回退到 `cherry_full`。

**建议**：
- 建立显式资源清单（`ASSETS` 对象），避免运行时扫描 styleSheets。
- 背景统一用 data URI 或预加载图片，SVG 立绘可继续保留。
- 增加 BGM/音效资源清单与懒加载。

### 7.6 测试增强
**建议**：
- 增加真实浏览器测试（Playwright），覆盖：
  - 标题页 → 序章 → 第2日选择 → 各女主个人线 → 结局。
  - 所有小游戏至少走一次 happy path。
  - 存/读档循环。
  - 流程图、CG 图鉴、关键词收集的解锁状态。
- 对 `script.js` 拆分后，保持 `story-graph.test.mjs` 的引用/可达性检查。
- 增加性能测试：大节点数下的内存占用、localStorage 大小限制检查。

## 八、后续内容开发方向

### 8.1 短期（1-2 个版本）
1. **补齐 Demo 到完整版**：目前大量 d6-d15 的节点是“长玩法链”，文本密度低。建议把 d6-d15 的每一天都变成有对话、有选择的真正章节，而不是纯玩法。
2. **增加男主个人线**：父母冷战、住校、自我认同 currently 只作为背景。可在真结局前增加一段“替自己回信”的专属剧情。
3. **循环叙事可视化**：在流程图中用不同颜色标记循环边、真结局条件、未解锁分支，让玩家更清晰。
4. **BAD 结局后引导**：进入 BAD 结局后，明确提示“这是其中一种可能”，并给玩家快速重开或跳转到第5日选择的入口。

### 8.2 中期（3-5 个版本）
1. **真结局后新增短篇**：
   - 学姐在新城市的视角短篇。
   - 三女主 GOOD 结局后各自的“一个月后”日常。
2. **增加支线角色**：
   - 田径社后辈、美术社同学、诗雨的竞争对手等，丰富校园生态。
   - 每个支线角色提供 1-2 个关键词和 CG。
3. **更深的多周目差异**：
   - 根据已解锁结局，让女主在下周目提前知道玩家“上一周目做过什么”。
   - 增加“回响”系统：上一周目的选择在下一周目以记忆碎片形式出现。
4. **手机端体验优化**：
   - 当前 UI 更适合桌面，需优化触控点击区域、虚拟键盘弹出时的布局、小游戏的触屏交互。

### 8.3 长期（完整版 / 商业化方向）
1. **美术升级**：
   - 将 SVG 立绘和 CG 替换为手绘插画。
   - 增加背景图、角色表情差分、动态粒子效果。
2. **声优与音乐**：

## 九、部署与工程化建议

### 9.1 增加 GitHub Actions
根据用户约定，服务器程序应增加 GitHub Actions。本项目虽为静态页面，但可部署到服务器或 GitHub Pages：

1. **构建/部署工作流**：
   - 每次 `push` 到 `main` 时运行 `npm test` 和 `npm run test:syntax`。
   - 通过后自动部署到服务器（rsync 或 scp）或 GitHub Pages。
2. **版本号自动递增**：
   - 脚本读取 `VERSION`，每次合并后自动 `+0.0.1`，满十进一。
   - 同步更新 `index.html` 中的 `?v=x.x.x` 缓存戳。
3. **Release 自动发布**：
   - 每次版本号变更自动生成 GitHub Release，附带变更摘要。

### 9.2 仓库治理
- `.gitignore` 已存在，建议增加：`node_modules/`、`.DS_Store`、构建产物、本地存档导出文件。
- 提交信息使用中文（已约定）。
- 创建 `docs/` 下的版本记录应继续保留，重大项目经验写入 `README.md`。

### 9.3 本地开发环境
- 用 Python 静态服务器或 `npx serve` 本地预览。
- 由于不在本机安装 MySQL 等服务，本项目无需后端数据库；若未来需要后端（如云存档、排行榜），优先用 Docker 或 serverless。

## 十二、总结

《樱时信笺》已经具备一部优秀视觉小说的骨架：主题统一、角色鲜明、循环叙事有收束、后日谈克制而温暖。当前最大的瓶颈是**代码体量和模块化程度**——两个 700KB 的文件承载了几乎所有内容与逻辑。

**下一步最核心的工作**：
1. 把剧本按章节拆成模块。
2. 把引擎按职责拆成模块。
3. 用通用模板重构重复小游戏。
4. 补齐 d6-d15 的叙事密度。

完成这四步后，项目将从“可运行的 Demo”升级为“可长期维护、可多人协作、可扩展的完整视觉小说基座”。
