# v3.4.61：告警链路的 JSON 转义修复（演练发现）

- 日期：2026-11-28 21:00
- 版本：v3.4.60 → v3.4.61
- 范围：`tools/box_cron_deploy.sh`、`tools/test_box_cron_deploy.sh`；无玩法与剧情改动

## 为什么做这次演练

v3.4.60 的失败告警只在离线测试里验证过：假 `verify_release.sh` 打印一句「假自检失败」，假 `curl` 记录调用。真实失败原因比测试长得多，而且带英文双引号（`name="gayme-account-api"`），这条路径没跑过。上线后如果自检真挂了、告警却发不出去，等于没有告警。

## 演练方法（不改线上配置）

1. 从盒子已安装的 `/root/sakura-deploy.sh` 里用 `awk` 抽出 `log()`、`notify()`、`public_verify()` 三个函数。
2. `PUBLIC_URL=http://127.0.0.1:9`（必然连不上），让 `public_verify()` 走失败分支。
3. 在 `PATH` 前面放一个只拦 `curl -X POST` 的包装脚本，把 Bark 的 HTTP 状态码和响应体落到 `/tmp/sakura-bark-*.txt`——`notify()` 自己会把 curl 输出丢进 `/dev/null`，不包一层看不到结果。
4. 整个演练只读线上、不改 nginx / 容器 / 仓库，唯一副作用是给 Bark 发一条真实通知。

演练脚本见盒子 `/tmp/bark-drill.sh`（临时文件，未入库）。

## 演练结果：告警没发出去

```
public_verify_rc=1
bark_http=400
bark_body={"code":400,"message":"request bind failed: invalid character 'g' after object key:value pair",...}
```

日志侧是通的：`!! 发版自检未通过（失败: GET /VERSION 返回 200（得到「000」...）；...）`，18 条失败原因全写进去了。

根因：`notify()` 手工拼 JSON：

```bash
-d "{\"title\":\"樱时信笺·发版自检\",\"body\":\"$1\"}"
```

`$1` 里的 `"` 没有转义，JSON 在 `name="gayme-account-api"` 处被截断；Bark 解析失败返回 400。也就是说：**自检失败时能不能收到告警，取决于失败原因里有没有引号**——而账号开关那一项的预期值恰好带两个引号。

顺带发现第二个问题：`awk` 把所有失败原因都拼进通知，18 条全长超过一屏，手机通知会被折叠得没法看。

## 修复

- `notify()` 改用 `python3 -c 'json.dumps(...)'` 生成载荷，`ensure_ascii=False` 保留中文；引号、反斜杠、换行都由序列化器处理。
- 失败原因只取前 3 条（`awk` 里 `if (n>=3) exit`），日志与通知都只保留前三条。
- `tools/test_box_cron_deploy.sh`：
  - 假 `verify_release.sh` 的失败输出改成 4 条，第一条带英文双引号；
  - 假 `curl` 把 `-d` 的载荷存到 `$FAKE/bark_payload`；
  - 新增断言：载荷能被 `json.load` 解析、正文与预期完全一致（引号保留、只 3 条）。

## 测试

- `bash tools/test_box_cron_deploy.sh`：全部通过（含新增两条断言）。
- `bash -n` 两个脚本通过。
- 其余基线（`npm test` 71/71、语法、账号 36/36、nginx 9 情形、发版自检 6 情形）在本次提交前一并复跑。

## 教训

- 「失败时告警」这种兜底路径，必须用**真实失败文本**验一次；测试里的假文本太干净，反而掩盖了转义 bug。
- 任何把外部文本塞进 JSON 的地方都不要手工拼字符串，统一走序列化。
- 演练时给 `curl` 包一层再断言状态码，否则 `notify()` 的 `>/dev/null` 会把证据一起丢掉。

## 回滚

只改两个 shell 脚本，`git revert` 本提交即可；线上部署脚本下次 cron 自动回退到旧版。旧版的问题是告警遇引号必失败，不建议回滚。
