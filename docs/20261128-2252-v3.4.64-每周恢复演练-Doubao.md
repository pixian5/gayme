# v3.4.64：每周自动做一次备份恢复演练

- 日期：2026-11-28 22:52
- 版本：v3.4.63 → v3.4.64
- 范围：`tools/box_backup.sh`；无玩法与剧情改动

## 问题

`box_backup.sh` 早就写了 `--verify`：把最新备份复制到临时目录、用正式镜像起一个只监听回环地址的临时实例、等 `/api/health` 通过、再用 `node:sqlite` 读出 `users` / `saves` 行数。但**没有任何计划任务调用它**——只有人手工跑才会演练。每日 03:30 的备份因此长期处于「文件存在、从未验证可恢复」的状态；磁盘写坏、备份中途截断都不会有人知道。

## 方案

新增 `--verify-only`：不产生新备份，只对最新备份做恢复演练（`--verify` 仍是「备份 + 演练」）。

`install_cron` 从一条计划任务变成两条，都用标记管理、重复安装幂等：

```
30 3 * * *  docker exec … backup_db.mjs …            # sakura-account-backup
10 4 * * 0  bash <脚本绝对路径> --verify-only --quiet  # sakura-account-verify
```

- 每周日 04:10 演练，避开 03:30 的备份；
- 脚本路径用 `readlink -f "$0"` 在安装时解析成绝对路径，换目录也能指向当前脚本；
- 摘除旧条目、条目数保护逻辑同时匹配两个标记，不会误删别人的计划任务；
- 演练失败会 `notify "账号数据库恢复演练失败"`，与备份失败、磁盘 80% 共用 `/root/.sakura-bark`。

顺手把备份脚本的 `notify()` 改成 `python3 json.dumps`——原来手拼 JSON 的写法与部署脚本 v3.4.61 修的 bug 同源，当前消息虽然不带引号，但以后改文案就可能踩到。

## 代价与风险

- 演练会起一个临时容器（`--rm`，端口 21100–21299 随机），持续几十秒；盒子内存足够，周日凌晨没有流量。
- 临时实例只挂载备份目录与只读的 `/app`，不碰正式数据库。
- 如果镜像被清理或端口冲突，演练会失败并告警；这类失败需要人看，不适合自动重试。
