## 一、问题定位（本次修复）

### P0-1　inbox 免费回信的记忆 id 被静默写错（引擎两套逻辑未同步）

`js/engine.js` 里 inbox 回信与 free letter 回信是两套独立实现：

- free letter（正确，v3.3.0 修过）：`const memId = typeof reply.memory === "string" ? reply.memory : reply.memory.id;`
- inbox（错误）：`Saves.saveMemory(matched[0].memory.id || matched[0].id, v)`

inbox 的 `matchings[].memory` 是**字符串**（如 `"诗雨·敢"`，`script.js:884`）。字符串取 `.id`
得 `undefined`，回退成 `matched[0].id`（`brave`/`calm`/…），图鉴出现英文键名条目，`"诗雨·敢"`
永远不解锁。

### P0-2　inbox 2 组分支互斥记忆共用 id（与 v3.3.2 同类）

覆盖「对象 + 字符串」两种写法的审计脚本发现重复 id 2 个：

| 共用 id | 分支 | 消息 |
|---|---|---|
| `诗雨·凌晨` | write_on（写下去）/ take_break（歇一歇） | msg_shiyu_night |
| `夏织·教练` | yes_run（还能跑）/ rest_first（先歇伤） | msg_xiazhi_coach |

`saveMemory` 按 id 去重 → 后走分支的记忆被吞、二周目也无法补齐。与 v3.3.2 修的 7 组同类，
只是藏在字符串写法里，被旧契约测试漏掉。

### P0-3　性格画像 8 维只用中文映射了 4 维

剧情/玩法实际写入 8 个性格维度（实测分布：honest 125 · kind 61 · careful 44 · brave 43 ·
active 14 · patient 11 · calm 7 · creative 3），但：

- `saves.js` 默认结构只有 `{brave,kind,active,honest}`，`getPersonalityProfile()` 标签也只输出 4 个；
- `engine.js` 画像面板 `dimName` 只映射 4 个 → `careful/patient/calm/creative`
  在「关于」页**直接显示英文键名**且不进标签。

## 五、经验

1. **同一功能的两套实现必须同步**：inbox 与 free letter 的 memory 取值逻辑分叉，
   v3.3.0 只修了一边，inbox 的同类 bug 又活了两个版本。
2. **契约测试的正则要覆盖数据的全部写法**：memory 有「对象」「字符串」两种写法，
   旧测试只覆盖对象 → 字符串里的重复 id 逃检两个版本。
3. **字符串取属性是隐形陷阱**：`"诗雨·敢".id === undefined`，配合 `|| fallback` 会静默用错值，
   不报错、不崩溃。凡「可能是字符串也可能是对象」的字段先 `typeof`。
4. **契约正则别匹配到「被断言的字段名本身」**：`memory: "..."` 的正则会命中
   `requires_memory: "..."`，让「requires_memory 引用有效」的断言恒真（自证）；用左界排除。
5. **图鉴/收集类系统要加可达性断言**：CG/结局/记忆每条都要有解锁点，否则死条目永远收集不全却无人报警。
