# 发版流程（两线共用规约）

> 2026-11-16 定稿，**2026-11-24 按 v3.4.55 的实际配置重写** · 适用：本地线与云端并行线（WorkBuddy / 任意协作者）
> 本文里的路径、远端、计划任务都是 2026-11-24 在盒子上实测的结果，不是转抄。

## 一、标准发版步骤（每次代码改动后）

```bash
# 0. 版本号 +0.0.1（规约：每轮改源码就升一次）
python3 tools/bump_version.py 3.4.XX
#    然后手工补两处：js/engine.js 头部注释加一行 v3.4.XX 说明 + GAME_CHANGELOG 数组首条

# 1. 测试：只在 InstaBox 盒子的测试目录 /data/home/gayme-test 跑（本机只改代码，不开浏览器、不出声）
#    把本地工作区（含未跟踪的新文件）打成压缩包推上去解压，再跑全量 16 套（清单见第二节）

# 2. 提交并推两个远端（顺序不要反：先 GitCode 再 GitHub 镜像）
git add -A && git commit -m "v3.4.XX：<中文说明>"
git push gitcode main && git push origin main
#    gitcode = 部署主源（盒子 cron 每 3 分钟从这里拉取）；origin = GitHub 镜像
#    AtomGit（atomgit.com）与 GitCode 是同一个仓库的两个域名，不要重复配置、不要重复核对

# 3. 部署：什么都不用做。盒子上的 root 计划任务每 3 分钟运行 /root/sakura-deploy.sh（仓库留档 tools/box_cron_deploy.sh）

# 4. 线上核对（见第四节）
```

**推送之前必须确认**：盒子上安装的部署脚本不比仓库里的旧。
v3.4.55 起脚本会在每次部署成功后自更新，一般不用管；只有当这次提交**改了部署脚本本身、
而且改的正是“部署这次提交要用到的步骤”**（例如 v3.4.55 的“打开账号开关”）时，要先手工装一次：

```bash
instabox cp tools/box_cron_deploy.sh sbjp:/data/home/sakura-deploy.sh.new
instabox exec sbjp -- 'sudo -n cp -p /root/sakura-deploy.sh /root/sakura-deploy.sh.bak-$(date +%Y%m%d) && sudo -n install -m 755 /data/home/sakura-deploy.sh.new /root/sakura-deploy.sh && rm /data/home/sakura-deploy.sh.new'
```

### 部署脚本每次运行做什么（`tools/box_cron_deploy.sh`）

1. 从 GitCode 拉取。拉取失败就保持现状，下次重试。
2. **自愈**（有没有新提交都做，平时只是几次文件读取）：站点版本与已部署提交对不上 → 重新同步；
   上次同步被确认不完整（`/var/lib/sakura-deploy/incomplete` 还在）→ 重新同步并核对；账号开关是关的 → 补打开。
3. 没有新提交 → 结束。这个提交上次部署失败过（`/var/lib/sakura-deploy/failed.sha`）→ 不再重试，等新提交。
4. **部署前备份数据库**（`tools/box_backup.sh --backup-only`）。备份失败则本次不部署。
   确实要跳过：`sudo touch /var/lib/sakura-deploy/skip-backup`（用完删掉）。
5. 同步站点根（按内容比较）并打开账号开关（`tools/patch_account_flag.py on`）；同步账号服务代码。
6. 只有 `server/` 有变化才重启账号容器（重启会中断在途请求、清空限流计数）。
7. **健康检查**：网页 200 → 站点文件与仓库逐文件一致 → `/api/health` 的 `database` 为 `ok` → 账号开关已打开。
8. 失败 → 回滚到上一个提交（站点与账号服务一起回滚并重启），再核对一次站点；仍不一致则留下 `incomplete` 标记，
   之后每次运行都会重试。记住失败提交，不再反复重试。
9. 刷新每日备份计划任务；部署脚本自更新（仓库版本与已安装版本不同时）。

日志：`/var/log/sakura-deploy.log`（一行一次事件；`!!` 开头是需要人看的）。

## 三、盒子测试环境（InstaBox · 盒子名 `sbjp`）

- 位置：`/data/home/gayme-test`（Node 22 + playwright + `/usr/bin/chromium` 已装；跑浏览器用例前 `export CHROME_PATH=/usr/bin/chromium`）。
- 把本地改动推上去：本地 `git ls-files -z --cached --others --exclude-standard` 打成压缩包 → `instabox cp` → 盒上解压覆盖。
  未提交的新文件也在包里，不必先提交。
- 长套件用 `nohup` 脱离会话跑并轮询汇总（`instabox exec` 单次上限 540 秒）。
- 盒子空闲 30 分钟自动暂停，`instabox exec sbjp -- '<命令>'` 会自动唤醒。
- 命令行会话过期（报 `session expired`）：`export INSTABOX_API_KEY=<密钥>` 即恢复。

## 五、换盒子 / 重建（材料都在仓库里，不靠记忆）

1. 装 Docker；克隆仓库到 `/data/home/gayme-deploy`（远端用带令牌的 GitCode 地址）。
2. 安装部署脚本与计划任务：
   ```bash
   sudo install -m 755 tools/box_cron_deploy.sh /root/sakura-deploy.sh
   (sudo crontab -l 2>/dev/null; echo "*/3 * * * * /root/sakura-deploy.sh >/dev/null 2>&1") | sudo crontab -
   ```
3. 网页服务器：`sakura-web` 容器（`nginx:alpine`，8090 端口），把 `/data/home/sakura` 只读挂到 `/usr/share/nginx/html`，
   配置目录 `/data/home/sakura-web/conf.d` 挂到 `/etc/nginx/conf.d`；`/api/` 反代到账号容器。
   首次部署脚本会把站点根同步出来（不需要新提交）。
4. 账号服务：`sakura-account` 容器（`node:24-bookworm-slim`），`/data/home/gayme-account/app` 只读挂到 `/app`，
   `/data/home/gayme-account/data` 挂到 `/data`，环境变量 `GAYME_DB_PATH=/data/game.db`、`GAYME_TRUST_PROXY=1`，
   重启策略 `unless-stopped`。把旧盒子的 `game.db` 复制到数据目录即可（启动时自动做表结构迁移）。
5. 备份：`sudo bash tools/box_backup.sh`（装每日 03:30 的计划任务并立即备份一次）；
   `sudo sh -c 'echo <Bark 推送地址> > /root/.sakura-bark && chmod 600 /root/.sakura-bark'`（失败告警通道）。
6. 跑一遍第四节的核对清单。
