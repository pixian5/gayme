## 代码托管（主项目 AtomGit，已被 2026-10-29 的 GitHub 方案取代，见下文）

- **主项目：AtomGit** https://atomgit.com/laotongtian/gayme（`origin`，2026-10-24 起）
- **备份：GitCode** https://gitcode.com/laotongtian/gayme（remote 名为 `gitcode`）
- AtomGit CLI（`ag`）登录：`printf '%s\n' '<token>' | ag auth login --with-token --force`
  （注意别用 heredoc，某些 shell 包装会把 heredoc 换行吞掉导致参数粘连）；
  登录后 `ag repo view laotongtian/gayme` 可查仓库
- git 远程用 token 形式：`https://oauth2:<token>@atomgit.com/<owner>/<repo>.git`
- 多远程策略：`git remote rename origin gitcode` + `git remote rename atomgit origin` 可把主项目切到 origin

- **2026-10-24：新增 GitCode 远程**（https://gitcode.com/laotongtian/gayme），与 gitee/github 并列，仅作代码托管，不影响部署链路

## GitCode 远程（2026-10-24 实测）

- 新建仓库入口：直接访问 `https://gitcode.com/create`（窄视口下"右上角新建"按钮会被隐藏；`/repos/new`、`/projects/new` 均 404）
- 登录判断：用户主页/项目列表是**公开页面**，不能凭"能看到"判断已登录；用受保护接口（`web-api.gitcode.com/api/v2/groups/user_groups/manageable_namespace`）的 401/200 判断最可靠
- HTTPS push：浏览器登录后系统 keychain 即有凭据，`git push` 直接可用，无需另配 PAT
- 建仓时**取消** README/.gitignore/LICENSE 初始化，避免与本地已有仓库冲突

## 当前发布流程（v3.2.3 起）

```bash
# 1) 本地开发：改代码 → bump_version.py → npm test + test:syntax + test:e2e
# 2) 提交推送双远程（gitee origin + github 备份）
# 3) 服务器自动部署：root cron 每 3 分钟执行 /usr/local/bin/sakura-deploy.sh
#    （git pull gitee 主源/github 备源 → rsync 到 /var/www/sakura → curl 校验版本）
# 4) 不阻塞等 CI——本地测试就是唯一门槛，push 完即可交付
```

## 服务器自动部署脚本（sakura-deploy.sh）

- 位置：`/usr/local/bin/sakura-deploy.sh`（root cron：`*/3 * * * * bash /usr/local/bin/sakura-deploy.sh`）
- 逻辑：仓库 `/opt/gayme-deploy`（首次自动 clone）→ fetch（gitee 失败自动切 github）→
  HEAD 变化或从未部署过才 rsync（`--delete` 清理旧文件）→ 写部署标记 `/var/run/sakura-last-deploy` → curl 校验线上版本
- 日志：`/var/log/sakura-deploy.log`
- **坑**：首次 clone 后 HEAD 与 origin/main 相同，若不记录"已部署标记"会跳过首次部署——用 LAST 标记区分"无更新"与"首次"

## 手动部署（回退手段）

```bash
bash tools/deploy.sh   # tar over SSH 直传 /var/www/sakura + 自动校验版本
# 支持 DEPLOY_HOST / DEPLOY_PORT / DEPLOY_USER / DEPLOY_KEY 环境变量，换服务器零改代码
```

## 避坑

- 服务器在美国（AWS），gitee 海外访问**不稳定**（实测多次 "连接被对方重置"，fetch 失败）；
  github 快且稳——脚本的双源回退（gitee 失败自动切 github）已兜底，但每次失败会多一次网络往返。
  若 gitee 频繁失败影响部署延迟，可把主源改为 github（拉取公开代码 ≠ 使用 GitHub CI/CD）
- /var/www/sakura 可写无需 sudo，但脚本整体用 root cron 跑，避免 /opt 权限与 git dubious ownership
- 上传脚本后注意：自动部署脚本**不能放在仓库目录内**（会被 git pull 覆盖），放 /usr/local/bin

## 云端测试（2026-10-29 实测，覆盖上文托管描述）

- 当前实际远程（2026-10-29 起）：`origin` = github.com/pixian5/gayme（**公开**，云端克隆主源）、
  `gitee` = gitee.com/ibjxk/gayme（服务器部署主源）、`gitcode` = 第三备份。
  上文「主项目 AtomGit」「origin = gitee」均为历史状态，已不适用。
- **`origin` 的命名是硬约束**：Trae「关联 GitHub 仓库」只认 `origin` 且域名为 github.com，
  所以托管平台（gitee/gitcode）不能占 `origin`；改名顺序：先
  `git remote rename origin gitee` 再 `git remote rename github origin`，最后
  `git branch -u origin/main main`（否则 `git push` 报 no upstream branch）。
- 云端跑测试的最小链路：`git clone https://github.com/pixian5/gayme.git` → `npm ci` →
  `npm test` + `npm run test:syntax`（无需浏览器）；跑 `test:e2e` / `test:graph` / `test:play`
  前需 `npx playwright install chromium`（约 150MB，一次性）。
- `npm ci` 只装 playwright 包、**不会**自动下载浏览器内核——云端第一次跑 e2e 报
  "Executable doesn't exist" 就是漏了 install 这一步，不是代码问题。
- pre-push 钩子只跑静态测试 + 语法 + `git diff --check`，云端可直接 push；
  `PREPUSH_E2E=1` 才会拉浏览器回归（云端没装内核时别开）。
- 三远程同一提交的判断：`git ls-remote --heads <remote>` 看 SHA 更可靠；本地 `git branch -vv`
  里的 tracking 引用可能滞后（本次 GitHub 实际落后 2 个提交，本地却显示已对齐，是上次 fetch 的旧值）。
- 云端在 GitHub 提交后，若要让服务器部署，必须再把 `main` 推到 gitee——部署链路只认 gitee 主源。
- 验证「云端可跑」的最低成本方法：`git clone --depth 1` 到 `/tmp` → `npm ci` → 逐个跑测试，
  一次暴露「素材未入库 / 依赖本地环境 / .gitignore 误伤」三类问题。

## Hugging Face Space 部署（2026-10-29 实测）

- 纯静态站用 **static SDK**：根 `README.md` 必须带 YAML frontmatter（`sdk: static`），
  项目自己的 README 通常没有 frontmatter → 单独维护一份（本项目 `tools/hf-space-readme.md`），
  部署时覆盖到 Space 根目录。
- **直连域名多一层 `.static`**：`https://<user>-<space>.static.hf.space/index.html`；
  `<user>-<space>.hf.space` 会返回 HF 官网 404 页。找不到真实地址就抓 Space 页面 HTML 搜
  `iframeSrc` / `embedSrc`。
- **HF 拒绝裸二进制**（错误提示 `Your push was rejected because it contains binary files`）：
  webp/jpg/png/ogg/woff2/svg 都要 LFS。做法：`.gitattributes` 补
  `*.webp filter=lfs diff=lfs merge=lfs -text` 等规则 → `git lfs install --local` →
  `git add --renormalize .`。若二进制已在上一提交里，还要 `git commit --amend`（或 rebase）
  重写，否则旧 blob 仍在推送范围内继续被拒。
- 二进制经 `302 → us.aws.cdn.hf.co/xet-bridge-us/...` 提供，跟随重定向后 MIME 正确
  （image/webp / audio/ogg / font/woff2），无需担心浏览器解码。
- Space 的 iframe 内（huggingface.co 页面）受第三方存储分区影响，`localStorage` 存档可能与
  直连不共享 → 对外给直连 `.static.hf.space` 地址。
- 部署只用环境变量传 `HF_TOKEN`，公开仓库里绝不能落盘 token；
  一键脚本见 `tools/deploy_hf.sh`（幂等：无变更时跳过推送，末尾轮询 `/VERSION` 校验）。
