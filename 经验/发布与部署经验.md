## 当前拓扑（2026-11-24 在盒子上实测，以此为准）

- **部署主源 = `gitcode`** https://gitcode.com/laotongtian/gayme → 盒子 root 计划任务每 3 分钟拉取并自动部署。
  盒上的部署克隆 `/data/home/gayme-deploy` **只配了这一个远端**——只推 GitHub 不会触发部署。
  AtomGit（atomgit.com）与 GitCode 是同一个仓库的两个域名，不是第三个远程。
- **镜像 = `origin` = GitHub** https://github.com/pixian5/gayme（公开）；持续集成（GitHub Actions）在这里跑。
  `origin` 这个名字固定给 GitHub（外部工具依赖这个命名），gitcode 不得占用。
- `gitee` 已在 2026-11-16 彻底移除。
- **教训**：2026-11-16 至 11-24 之间文档一直写「GitHub 是部署主源」，与盒子实际配置相反，
  发版流程文档和 README 都照抄了这个错误。写部署文档前先到盒子上 `git config --get remote.origin.url` 看一眼。
- 发版后核对两个远程指向同一提交：`git ls-remote gitcode main` 与 `git ls-remote origin main`
  （旧写法 `git ls-remote --heads origin gitcode` 是错的——第二个参数是「引用名匹配模式」，不会去查 gitcode 远程）。
- 唯一线上入口：InstaBox 盒子 8090（盒子名 `sbjp`，曾名 box-c6119b、xjp）；HF Space 停在 v3.4.43 不再更新。
- 完整步骤见 `docs/发版流程.md`（2026-11-24 重写）。
- **发版后自检用脚本，不要手 curl 两条地址**（v3.4.59 起）：`bash tools/verify_release.sh --with-box`。
  它一次核对站点与账号版本、`/api/health`、两站点 XFO/CSP、`?v=` 与 `sw.js` 缓存仓、七个敏感路径 404；
  任何不一致非零退出。手查最容易漏的正是「站点已是新版、账号服务还报旧版」。
- **解析响应头先统一小写**：线上 nginx 走 HTTP/2 时头名小写，本地假站点常见大写；
  macOS 自带 awk 不支持 `IGNORECASE`，按大写写死会在离线测试里误报。比较时忽略大小写。
- **离线假站点的后台进程必须重定向输出**：若它继承了调用方 stdout 管道，脚本结束后管道不关，
  CI/终端会一直等 EOF，表现为「测试卡死」。退出时先 `kill`（必要时 `-9`）再清目录。
- **部署成功不等于线上正确**（v3.4.60 起）：部署脚本在本地健康检查通过后会自动跑一次
  `verify_release.sh`，核对公网版本、账号健康、两站点响应头、缓存仓与敏感目录。
  失败**不回滚**——nginx 头、DNS、缓存都不在仓库里，回滚代码解决不了，只会把可用站点拉回旧版；
  正确处理是写日志 + Bark 告警，人再处理。
- **自检只在新提交时跑**：脚本在 `PREV = CUR` 时提前退出，所以自愈/补文件不会每 3 分钟推一次告警。
  自检失败也不写 `failed.sha`，否则这个提交再也不会被重试。
- **BSD 的 `tr` 不能拿多字节字符当替换目标**：`tr '\n' '；'` 在 macOS 上会截断成乱码。
  拼接多行文本用 `awk` 显式打印分隔符。

## 盒子部署脚本（v3.4.55 入库并加固，2026-11-24）

脚本就是仓库里的 `tools/box_cron_deploy.sh`，盒子上装成 `/root/sakura-deploy.sh`，每次部署成功后自更新。
离线流程测试 `bash tools/test_box_cron_deploy.sh`（104 条断言）。这一轮付过学费的：

- **rsync 默认只比「大小 + 修改时间（精确到秒）」**：同一秒内先后部署两个同大小文件（`3.4.55` 与 `3.4.58`
  都是 7 个字节）会被当成没变化而不拷贝。站点只有 15MB，直接加 `--checksum` 按内容比较。
- **同步完要逐文件核对**：`rsync -a --checksum --delete --delete-excluded … --dry-run --itemize-changes` 的输出里，
  以 `>f` 开头或 `*deleting` 开头的行就是「还有差异」；只看内容，时间戳差异（`.f..t……`）不算。
  磁盘写满、同步中途被打断都会留下新旧混杂的文件，光看网页返回 200 发现不了。
- **测试脚手架里「开发者目录」和「部署克隆」必须是两个目录**：做成本地提交、脚本 fetch 的同一个目录，
  HEAD 永远等于远端最新，脚本永远判定「无新提交」，所有断言全红，很容易误以为是脚本坏了。
- **克隆空的裸仓库要先指定默认分支**：本机默认分支是 `master`，线上是 `main`，首次克隆拿不到 HEAD。
- **自愈要放在「失败过的提交不再重试」之前**：回滚之后失败的提交仍是远端最新，脚本在那个判断处直接退出，
  根本走不到「补齐」那一步。
- **自愈的顺序**：先同步站点，再看同步是否完整，最后才单独看账号开关。顺序反了会在站点目录为空时
  （换盒子）先报一次「开关自愈失败」的假告警。
- **修不好的事情不要反复报**：记一次日志 + 留一个状态标记，之后每次运行静默重试，成功后才再写一行。
  否则故障期间每 3 分钟刷一行。
- **命令行工具的成功输出不要进日志**：部署脚本每次同步都会调用补丁工具，工具每次都打印一行「已打开」，
  故障期间就成了刷屏。成功输出丢弃，只把错误（标准错误）写进日志。
- **部署脚本自更新**：先写临时文件再改名（原子替换）。正在运行的脚本读的是旧文件，不受影响。
- **改了部署脚本本身时，上线顺序是「先装脚本，再推提交」**：旧脚本部署新提交时还没有新步骤
  （例如打开账号开关），而之后「无新提交就提前退出」的路径不会再补做。
- **站点根要用排除法之外的第二道防线**：v3.4.55 实测发现仓库根目录的 `dist/`（itch 上架截图）和
  `scripts/check-meta.mjs` 被同步进了公开目录、公网可以下载。内容无害，但以后新增的仓库根文件仍可能中招。
  更稳的做法是只同步运行文件白名单（已列入下一步待实现）。
- **上线前做一次只读预演**：用健康检查同款的 rsync 试运行命令比较「线上站点根」与「部署克隆」，
  能提前看到这次部署到底会改动哪些线上文件、有没有别的部署通道留下的补丁会被冲掉。

## nginx 配置补丁（v3.4.56 起，`tools/patch_nginx_account.py`；v3.4.57 补防嵌入）

nginx 配置不在站点根里，不随自动部署走，要手工在盒子上打补丁（`tools/deploy_box.sh` 会顺带执行）。

- **先在内存里把所有配置都改好，再落盘**：原实现改完第一份就写盘，第二份若被拒绝（认不出的写法、找不到锚点），
  就会留下「磁盘上已改、却没经过语法检查也没重载」的半成品。现在任何一份被拒绝就一份都不写。
- **`nginx -t` 不通过就恢复备份、不重载**；每份改动过的配置都先备份。
  **新建的文件也要能回滚**：新建的 `security_headers.conf` 没有备份，失败时必须 `unlink`，否则回滚不完整。
- **路径用环境变量可改写、docker 用 PATH 里的假命令顶替**，这样才能写离线测试（`bash tools/test_nginx_patch.sh`，
  9 类情形，不碰线上配置）。补丁工具改一次就跑一遍。
- **`add_header` 的继承是有条件的**：只有当前层级没写 `add_header` 时，才继承上一级。所以防嵌入头不能只写
  server 级——任何自己写了 `add_header` 的 `location` 都会把 server 级整组丢掉。做法是 server 级与每个
  `location` 各 `include` 一次；重复 include 不会产生重复响应头（location 自己那组覆盖继承）。
- **两个站点各放一份安全头文件**：8090 与 2096 是两套独立挂载，`include /etc/nginx/conf.d/security_headers.conf;`
  在容器里是同名路径，但宿主机上分别在两个 `conf.d` 目录。只建一份，另一个站点 `nginx -t` 会失败。
- **补文件与改配置要解耦**：从上一版升上来时，配置可能已经引用了安全头文件、只是文件缺内容；这一步不能
  挂在「配置有没有改动」的分支上，否则永远不会执行。
- **上线顺序取决于两项改动谁兼容谁**：「原样透传转发地址头」（nginx）先于「取最后一项」（服务端）上线是安全的，
  反过来不行。写进发版流程：带 nginx 配置改动的版本先打补丁再推代码。
- **站点根用「排除法 + 分类契约」，而不是白名单**：白名单的失误模式是新资源没进名单、线上 404，且完整性检查用的是
  同一份名单、发现不了；排除法的失误模式是非运行文件被发布，可以在 `npm test` 阶段用契约拦住
  （仓库根目录每个条目必须登记为运行文件或不进公开目录）。
- **`server_tokens off` 只能去掉版本号**，响应头仍是 `server: nginx`；要彻底去掉这个头需要额外模块，nginx:alpine 没有。
- **防嵌入只能由响应头管**：页面 `meta` 的 CSP 不支持 `frame-ancestors`；COOP 管弹窗隔离、CORP 管资源引用，
  都拦不住 iframe。只有 `X-Frame-Options` 或响应头版 `Content-Security-Policy: frame-ancestors` 有效；
  Node 直接服务的页面由 `server/index.mjs` 发，nginx 静态站要在 nginx 发。
- **`patch_nginx_account.py` 的半成品会静默坏掉**：调用未定义函数（`NameError`）、测试预期与新逻辑相反、
  「配置没变只补文件」的分支被反向限制——这三种都不会在正常路径暴露，只有跑离线测试才看得见。
  改完工具先跑测试，再谈上线。

## 本机网络出口故障时怎么判断（2026-11-24 实测）

- 现象：`instabox exec`、`instabox ls`、GitHub 接口全部 `EOF` / 握手失败，GitCode 正常。
- 判断方法：`curl -w "%{time_connect} %{remote_ip}"` 看连接耗时——到境外地址 6 毫秒就「连上」说明走的是本机网络层的
  代理通道；随后 TLS 握手被断，而境内地址正常，就是代理通道的上游出了故障，不是盒子挂了。
- 处理：等它恢复（循环探测），期间做不需要联网的工作（写文档、本地提交）。本机没有配置系统代理时也会有这种现象，
  别去改系统代理设置。
- 另一个偶发问题：`instabox cp` 传 13MB 的包时接口中断（EOF），文件没传上去。上传后核对压缩包的校验和再解压；
  链条里任何一步失败都要停下来，不要继续。

## 旧的常驻服务器部署脚本（历史，AWS 时期，仅供追溯）

- 位置：`/usr/local/bin/sakura-deploy.sh`（root cron：`*/3 * * * * bash /usr/local/bin/sakura-deploy.sh`）
- 逻辑：仓库 `/opt/gayme-deploy`（首次自动 clone）→ fetch（gitee 失败自动切 github）→
  HEAD 变化或从未部署过才 rsync（`--delete` 清理旧文件）→ 写部署标记 `/var/run/sakura-last-deploy` → curl 校验线上版本
- 日志：`/var/log/sakura-deploy.log`
- **坑**：首次 clone 后 HEAD 与 origin/main 相同，若不记录"已部署标记"会跳过首次部署——用 LAST 标记区分"无更新"与"首次"

## 避坑

- 服务器在美国（AWS），gitee 海外访问**不稳定**（实测多次 "连接被对方重置"，fetch 失败）；
  github 快且稳——脚本的双源回退（gitee 失败自动切 github）已兜底，但每次失败会多一次网络往返。
  若 gitee 频繁失败影响部署延迟，可把主源改为 github（拉取公开代码 ≠ 使用 GitHub CI/CD）
- /var/www/sakura 可写无需 sudo，但脚本整体用 root cron 跑，避免 /opt 权限与 git dubious ownership
- 上传脚本后注意：自动部署脚本**不能放在仓库目录内**（会被 git pull 覆盖），放 /usr/local/bin

## 云端测试（2026-10-29 实测，覆盖上文托管描述）

- 当前实际远程（2026-11-01 最终确认，**用户明确要求：`origin` 始终 = GitHub，不得再改回**）：
  `origin` = github.com/pixian5/gayme（**公开**，云端克隆主源）、
  `gitee` = gitee.com/ibjxk/gayme（服务器部署主源）、`gitcode` = 第三备份。
  上文「主项目 AtomGit」「origin = gitee」均为历史状态，已不适用。
- **`origin` 的命名是硬约束**：Trae「关联 GitHub 仓库」只认 `origin` 且域名为 github.com，
  所以托管平台（gitee/gitcode）不能占 `origin`；改名顺序：先
  `git remote rename origin gitee` 再 `git remote rename github origin`，最后
  `git branch -u origin/main main`（否则 `git push` 报 no upstream branch）。
  互换后自查三项：`git branch -vv` 显示 `[origin/main]`、`git config branch.main.remote` = origin、
  `git remote -v` 里 origin 的域名是 github.com（`git remote rename` 会自动迁移 remote-tracking 引用，
  本地提交不会丢；仓库内的 pre-push 钩子与 `tools/deploy.sh` 都不依赖远程名，可安全互换）。
- 云端跑测试的最小链路：`git clone https://github.com/pixian5/gayme.git` → `npm ci` →
  `npm test` + `npm run test:syntax`（无需浏览器）；跑 `test:e2e` / `test:graph` / `test:play`
  前需 `npx playwright install chromium`（约 150MB，一次性）。
- `npm ci` 只装 playwright 包、**不会**自动下载浏览器内核——云端第一次跑 e2e 报
  "Executable doesn't exist" 就是漏了 install 这一步，不是代码问题。
- pre-push 钩子只跑静态测试 + 语法 + `git diff --check`，云端可直接 push；
  `PREPUSH_E2E=1` 才会拉浏览器回归（云端没装内核时别开）。
- 三远程同一提交的判断：`git ls-remote --heads <remote>` 看 SHA 更可靠；本地 `git branch -vv`
  里的 tracking 引用可能滞后（本次 GitHub 实际落后 2 个提交，本地却显示已对齐，是上次 fetch 的旧值）。
- 云端在 GitHub 提交后，若要让服务器部署，必须再把 `main` 推到 gitee——部署链路只认 gitee 主源。
- 验证「云端可跑」的最低成本方法：`git clone --depth 1` 到 `/tmp` → `npm ci` → 逐个跑测试，
  一次暴露「素材未入库 / 依赖本地环境 / .gitignore 误伤」三类问题。

## GitHub 推送（2026-11-01 实测）

- **先验证凭据与仓库，再推**：`curl -sS -H "Authorization: Bearer <TOKEN>" https://api.github.com/user`
  （200 = 令牌有效）；`https://api.github.com/repos/<owner>/<repo>` 看 `private`（本项目为公开仓库，
  源码对外可见）、`default_branch`、`pushed_at`。
- **curl 通 ≠ git 能推**：判定远端可达要用 `git ls-remote <remote>`，而且**不要接 `| head`**——
  管道的退出码是 head 的，失败会被伪装成「空输出」，本次就因此误判 GitHub 是空仓库。
- **`GnuTLS recv error (-110)`**：沙箱 git 用 GnuTLS，上传约 17MB pack 时 TLS 被中断
  （curl 同域名 HTTP/2 正常）。解法：`git config http.postBuffer 524288000`，必要时再
  `git config http.version HTTP/1.1`。改完即推成功（`4e899f5..c0e35e8 main -> main`）。
- **凭据落盘位置**：令牌写进 remote URL 只存在于本地 `.git/config`，不会进版本库；
  换机器克隆时用干净地址，别把带令牌的 URL 抄进文档或脚本。
- **只推主线也要看分支**：GitHub 上还有 `gh-pages`（跳转页），push 默认不动其他分支，
  无需特殊处理，但推完可 `git ls-remote --heads <remote>` 确认分支都在。

## Hugging Face Space 部署（2026-10-29 实测）

- 纯静态站用 **static SDK**：根 `README.md` 必须带 YAML frontmatter（`sdk: static`），
  项目自己的 README 通常没有 frontmatter → 单独维护一份（本项目 `tools/hf-space-readme.md`），
  部署时覆盖到 Space 根目录。
- **直连域名多一层 `.static`**：`https://<user>-<space>.static.hf.space/index.html`；
  `<user>-<space>.hf.space` 会返回 HF 官网 404 页。找不到真实地址就抓 Space 页面 HTML 搜
  `iframeSrc` / `embedSrc`。
- **HF 拒绝裸二进制**（错误提示 `Your push was rejected because it contains binary files`）：
  webp/jpg/png/ogg/woff2/svg 都要 LFS。做法：`.gitattributes` 补
  `*.webp filter=lfs diff=lfs merge=lfs -text` 等规则 → `git lfs install --local` →
  `git add --renormalize .`。若二进制已在上一提交里，还要 `git commit --amend`（或 rebase）
  重写，否则旧 blob 仍在推送范围内继续被拒。
- 二进制经 `302 → us.aws.cdn.hf.co/xet-bridge-us/...` 提供，跟随重定向后 MIME 正确
  （image/webp / audio/ogg / font/woff2），无需担心浏览器解码。
- Space 的 iframe 内（huggingface.co 页面）受第三方存储分区影响，`localStorage` 存档可能与
  直连不共享 → 对外给直连 `.static.hf.space` 地址。
- 部署只用环境变量传 `HF_TOKEN`，公开仓库里绝不能落盘 token；
  一键脚本见 `tools/deploy_hf.sh`（幂等：无变更时跳过推送，末尾轮询 `/VERSION` 校验）。

## 强推会卡住服务器自动部署（v3.4.33 实测教训）

- 服务器 cron（每 3 分钟）从 gitee 拉取自动部署。我为了合入 gitcode 上的并行提交做了
  `git pull --rebase`，把**已经推送到 gitee 的提交改写了历史**，随后强推。结果服务器上
  的本地分支与新远程历史不再成祖先关系，pull 无法 fast-forward，线上连等 10 分钟仍停在旧版本。
- **补救**：在本地基于**服务器所在的旧提交**再做一个 merge 提交（把新线合进来），
  这样新提交是旧提交的后代，服务器就能正常 ff 拉取。内容不变（`git diff 旧 main` 为空），
  只是多一个 merge 提交换回可 ff 的历史。
- **更好的做法（下次起）**：先 `git fetch` 所有远程，**确认没有并行提交再 rebase**；
  一旦提交已经推到 gitee（部署源），后续整理历史一律用 merge 而不是 rebase。
  确实需要强推时，推完要盯线上版本串，超时不更新就按上面的方法补一个 merge 提交。

## HF Space 线上真人试玩方法与流量实测（2026-11-06 实测）

- **线上试玩要带 Service Worker**：本地 e2e 一律 `serviceWorkers: "block"` 是为了确定性；
  验证线上部署时反过来——**不屏蔽 SW**，否则测不出「老玩家回访」的真实体验。
  用 `chromium.launchPersistentContext("/tmp/xxx-profile")` 跨进程共享 SW/HTTP 缓存。
- **流量实测数字**（v3.4.25，BGM 静音，整局通关）：首进站约 2.83MB / 46 请求
  （音频是运行时缓存且静音玩家不触发下载）；回访 46/46 响应全部由 SW 缓存直供，
  出网≈0——三层缓存设计在生产环境成立，可放心对手机流量玩家宣传「下载一次，之后随便玩」。

## InstaBox 盒子当服务器：能做什么、不能做什么（2026-11-07 实测）

- **没有公网入站**。`curl icanhazip` 拿到的是出网 NAT 的 egress IP，不路由入站；
  `nc -z` 显示端口"通"是平台边缘代答 SYN 的假象。判定真入站的唯一方法：
  盒内起临时 HTTP 服务，外部直连 IP 试（HTTP 000 = 无入站）。
- 唯一公网入口：`instabox port publish` 发布端口，URL 形如
  `https://<port>-<boxid>.instabox.tech`，TLS 由平台边缘终结（*.instabox.tech），
  **自有域名 + 自己证书 + 固定端口的老架构在盒子上不可能复活**。
- 部署链路：push gitee → 盒子 root cron（/root/sakura-deploy.sh，gitee 主源→github 备源
  → rsync --delete-excluded → 健康检查 → 失败回滚）；手动直推用 `tools/deploy_box.sh`。
- **instabox push 的落盘语义**：目录会以本地目录名嵌套落到目标下（推 `.` 到
  /data/xxx 会得到 /data/xxx/gayme/），所以先推暂存区、再盒内 rsync 同步。
- 盒子可以和别的项目混部，但要先盘清占用：127.0.0.1:8080（另一项目的 python 服务）、
  宿主 8443、bz/xbz systemd 服务。部署新东西前先 `ss -tln` 全量看端口。
- acme.sh 通配符证书（DNS-01）在盒子上可直接只读挂载进 nginx 容器备用；等哪天有
  真实入站的主机，证书+配置原样迁移即插即用。
- 自有域名要指向无入站的源（如 HF Space）：CNAME（橙云）+ **Origin Rule 改写 Host 头**
  ——CF 源站连接的 SNI 随改写后的 Host 走，SaaS 源才能按正确 Host 路由。
  cfut_ 令牌只有 DNS 权限，Rulesets（Origin/Redirect Rule）必须面板点。

## AtomGit 与 GitCode 是同一个仓库（2026-11-20 用户澄清）

- `atomgit.com/laotongtian/gayme` 与 `gitcode.com/laotongtian/gayme` **指向同一份代码**
  （同仓库两个域名/两个入口），不是三个独立远程。核对同步状态时只算两条：
  `origin`(GitHub) + `gitcode`(GitCode/AtomGit)。
- 不要为 AtomGit 单独 `git remote add`，也不要在"三远程是否一致"的检查里把它当第三条；
  否则会得出"某端落后"的假结论，浪费一轮排查。
- 推送走 `gitcode` remote 即可（AtomGit 域名同一仓库，随之一致）。
